Today

On main, with tests.

Each row names its header in include/lv/, then its test in tests/.

  • Enumerators by name An LVGL enumerator is a name in quotes, in a tree, a style or set(): .align = "center". A wrong name is a compile error that lists the names. The examples name nothing of LVGL's C API, and a test keeps it so. detail/enum_names.hpp, values.hpp; enum_names.cpp, fail/enumerator_unknown_name.cpp, examples_check
  • Documentation A quick start that a test builds as a project of its own. The pages are Markdown in docs/, rendered into this site, and published for agents as llms.txt, llms-full.txt and one Markdown file a page. docs/, tools/docs.py; quick_start, quick_start_picture, docs_check
  • A small core header <lv/lv.hpp> holds what nearly every program writes; a theme, a look, fonts, pictures, lists, repetition, documents, slots and the pointer each have a header of their own, and <lv/all.hpp> includes them all. A file that includes only the core compiles in 31 percent fewer instructions. A build through lvgl26's CMake stops at a missing header with main.cpp:12: lv::list needs #include <lv/list.hpp>, and clangd offers the include as a quick fix. See Which header. lv/lv.hpp, lv/all.hpp, tools/check_includes.py; include_only.cpp, includes_check, headers_data
  • Editor support One CMake line, lvgl26_editor_support(), gives clangd stub headers of the public API. The editor then completes the members of lv::arc({., shows what each takes, and marks a wrong name in quotes. See Editor support. cmake/editor.cmake, tools/editor/; the editor_* tests, in a CI job of their own with Clang 21
  • Start-up without C lv::application starts LVGL and stops it when it goes out of scope; run() is the loop. lv::display draws into an lv::frame or an lv::band and tells a panel function what was drawn. A program calls no lv_init and no lv_display_*. application.hpp, display.hpp, host.hpp; application.cpp
  • Typed views lv::view<"arc"> is one pointer and never deletes. lv::owned<T> owns. lv::weak<T> empties itself when LVGL deletes the widget. view.hpp, owned.hpp; l1_views.cpp
  • Generated properties lv::props<"arc">: one member per lv_arc_set_* and lv_obj_set_* function and one per event, built by reflection from LVGL's headers. props.hpp, events.hpp; l1_views.cpp, l2_tree.cpp
  • Compile-time tree lv::column, lv::row, lv::group and 13 widgets by short name. lv::widget<"spinbox"> reaches every other widget. Ids, lv::mount, typed get<"id">. A tree and a set call the setters in the order of the properties, except where LVGL needs another: a button matrix's map first and its controls last, a text area's cursor after its text. tree.hpp, detail/setter_order.hpp; l2_tree.cpp, setter_order.cpp, ref/slice.png
  • Fonts drawn once A file that names lv::font_of<"text.title"> holds the address of an object that another file defines, so the compiler draws each font once for the program and the files that draw fonts build side by side. The name is checked against the token file, and the build says which font_*.cpp is missing. The picture and the linked sections are the same as with the font drawn in place. look.hpp, cmake/check_fonts.cmake; fonts_split, check_fonts_*, examples/fonts_split
  • Signal's fonts linked once The library lvgl26::signal_type draws Signal's eight text styles, each in a file of its own, and lv/signal_fonts.hpp names them: a file that uses Signal's themes with fonts compiles in about a third of the time of lv/signal_type.hpp, and the pictures are the same. Optional, off by default. lv/signal_fonts.hpp, lib/signal_type; signal_linked, signal_fonts_and_type
  • One format for UI code A .clang-format and a small pass that changes white space only lay out every example: two spaces, children as arguments, one property per line after a trailing comma, .style = { on one line. A check in CI fails on an example that would change, and the pages that copy the examples follow. .clang-format, tools/format_ui.py, tools/call_form.py; editor_format_examples, editor_format_ui
  • Children as arguments lv::group({...}, lv::label({...}), lv::button({...})): the properties first, then each child, so a formatter lays the tree out as nested blocks. lv::each(rows, &row::id, {...}, row), lv::shown(state, arms...) and lv::when(flag, tree) take theirs the same way, and [...] still builds the same node. Anything after the properties that is no child is a compile error that shows the form. tree.hpp, list.hpp, shown.hpp; editor/api_uses.cpp, fail/children_*.cpp, examples/lists
  • A mounted tree where the program puts it lv::mounted owns the widgets and holds what the tree's nodes keep at run time, sized by the compiler: lvgl26 allocates nothing for it. It never moves. It lives in a variable, or in a constinit global with mount(parent) and unmount(), for a window that opens and closes in the same memory; lv::mount_in takes a slice of a region. It carries its own failure: if (!root), root.error(). See Where a tree lives. tree.hpp; mounted_storage.cpp, fail/*_storage.cpp, examples/mounting
  • Pages that follow a state lv::shown(current)[lv::is<page::home>(home), lv::is<page::settings>(settings), lv::otherwise()] shows the tree of the value of a state of an enum or a bool, and lv::when(offline)[banner] a tree while a flag is true. Every value has one arm, checked at compile time. lv::shown(current, {.enter = slide_in, .leave = slide_out}) slides pages with lv::transition: the new page is built before the old one leaves, a page asked for again turns round where it stands, and a leaving page takes no clicks. .on_shown runs when a page is built, .on_front each time it comes to the front. With .alive = 4 the pages shown most recently stay built and hidden, and come back without being built again. A page of another file is extern const lv::page home_page;, defined there as lv::page_of<ui>, with no size written anywhere. The pages live in two slots of the size of the largest, in the tree's storage or taken once from LVGL's heap at mount; a switch allocates nothing of lvgl26's. A change is shown before the next frame; lv::settle() shows it at once. The printer port has no pager of its own any more. shown.hpp, detail/deferred.hpp; shown.cpp, shown_transitions.cpp, fail/shown_*.cpp, examples/pages, examples/ports/slint/printer
  • One slot for one of several trees lv::one_of<saving, failed> holds one tree at a time in the memory of the largest, as std::variant does, and carries its failure as lv::mounted does. mount<T>(parent) ends the tree that is there first; switching allocates nothing. visit takes functions whose parameter type is the pattern: lv::held<failed>, a handle checked at each use, auto for the other trees, lv::not_mounted for the empty slot. For a root: pages inside a tree are lv::shown. See Where a tree lives. one_of.hpp, detail/one_of_region.hpp; one_of.cpp, fail/one_of_*.cpp, fail/visit_*.cpp, examples/mounting
  • A pointer without C lv::pointer mouse{display} is a mouse or a touch panel fed by the platform: press, move, release. A queue in the object keeps a press shorter than LVGL's read period, and LVGL reads it at the next step; lv::pointer panel{display, &read} is asked instead. The window examples feed it from SDL through examples/platform/sdl_window.hpp, and the browser page of examples/wasm from its events; one application source runs in both, with no C call. See A pointer. pointer.hpp, detail/input_queue.hpp; pointer.cpp, window_app.cpp, fail/pointer_*.cpp, examples/window
  • A window in the application's loop A program ends with return app.run(); in a window as on a device: a platform object joins the loop with lv::in_loop and is polled before each step, without an allocation. Closing the window ends run() unless the program takes the request; window.hide() and show() keep its trees, and a display that is not visible() draws nothing. A host that owns the loop calls step(). See A pointer. application.hpp, display.hpp, pointer.hpp; app_loop.cpp, window_behaviour, examples/window
  • Units and values px, pct, deg, ms, sec, lv::size_content. Horizontal and vertical lengths are different kinds. Integers reject bool, floating point and values that do not fit. units.hpp, values.hpp; units.cpp, values.cpp
  • Angles in the unit LVGL means Whole degrees are an lv::angle; the few values LVGL takes in tenths of a degree (an image's rotation, a style's transform rotation and skew) are lv::decidegrees. 90 * deg works for both, 22.5 * deg only where tenths are taken. Which is which is read from LVGL's doc comments at compile time, and a test checks it against the pixels. units.hpp, detail/angle_docs.hpp; angle_units.cpp
  • Styles Style properties in the tree, merged with |, stored as const lv_style_t. A design value must be a token, or lv::raw(...). A part in a state is a selector: base | lv::on("knob", "pressed", {...}), in a node or a theme, a constant with no heap. style.hpp; styles.cpp, style_selectors.cpp, ref/styled.png
  • Images decoded on the device lv::encoded_image keeps a PNG or a baseline JPEG as its file, and LVGL's decoder draws it. For photos and large pictures. The decoders are behind the CMake options LVGL26_PNG and LVGL26_JPEG. lv/encoded_image.hpp, tests/encoded_image.cpp
  • Images from PNG files The compiler decodes an embedded PNG and stores its pixels in the display's own format: RGB565 or XRGB8888 when opaque, with alpha when see-through. No decoder and no heap on the device. A project setting limits the size. lv/image.hpp, tests/image.cpp, examples/images
  • Fonts drawn on the device lv::scaled_font owns a font that LVGL's TinyTTF draws from an embedded .ttf. A style binds to it, and every bound widget follows resize. It is behind the CMake option LVGL26_TTF. lv/scaled_font.hpp, tests/scaled_font.cpp, examples/scaled_font
  • Fonts from TrueType files The compiler reads an embedded .ttf and makes a constant font: glyphs at 4 bits per pixel and kerning in read-only memory, no heap, no converter. lv::typeface gives a typography token its font; a font without a token needs lv::raw. lv/font.hpp, tests/font.cpp, examples/fonts
  • Design tokens W3C DTCG JSON read at compile time through #embed: colors, dimensions, durations, numbers, font family and weight, easing curves, shadow, border, typography, transition and gradient. Aliases are resolved. tokens.hpp, token_types.hpp; tokens.cpp, ref/tokens_dark.png, ref/tokens_light.png
  • Named looks .style = lv::look<"queue.card"> turns a group of the project's design tokens into a constant style: each entry is matched to the style property of the same name and checked against its type (colors, dimensions, opacities, fonts drawn by the compiler, shadow, border and transition tokens). A nested group is a layer and must be named like a state or part; a variant is a sibling group, and lv::look<"tile tile-print"> stacks looks, a later one winning. LVGL values by name and percentages come from the group's $extensions, and a color with an alpha sets its opacity, so the token file stays standard. lv::look_of<"tile", E> names a look for an enumerator. A project names its token file once, with a specialization of lv::design; a part takes the design as a template parameter. A misspelled path, an entry that fits no property and a value of the wrong type are compile errors that say what is valid, and the editor marks an unknown path. tools/look_groups.py lists the groups that no look names. See Looks. look.hpp, tree.hpp; look.cpp, looks_example.cpp, fail/look_*.cpp, editor/wrong_look.cpp, examples/looks
  • Themes lv::theme({...}) gives every widget of a kind its styles, for its parts and states, and a display takes it as its last argument. The styles are constants in read-only memory. lv::signal::dark and lv::signal::day are built in. LVGL26_NO_DEFAULT_THEME drops LVGL's own theme and its 2.5 KB of heap. lv/theme.hpp, lv/signal.hpp, tests/theme.cpp, tests/signal.cpp, tests/no_default_theme.cpp, examples/theme
  • Signal's typefaces lv/signal_type.hpp makes Signal's fonts from its typography tokens. lv::signal::dark_with_type and lv::signal::day_with_type set all text in Barlow and the text of a button in Barlow Condensed. lv::signal::numerals makes a font with the sixteen characters of a reading. lv/signal.hpp alone draws no font, so it compiles as fast as before. lv/signal_type.hpp, tests/signal_type.cpp, ref/signal_type_dark.png, ref/signal_type_day.png, fail/signal_numerals_not_a_numeral.cpp, examples/signal_type
  • Signal's tell-tale lamps lv/signal_lamps.hpp gives the green and the blue that the law defines for tell-tale lamps, for the dark and the day theme: lv::signal::lamps.dark.green. They are a header of their own, so lv/signal.hpp costs what it did. lv/signal_lamps.hpp, include/lv/signal/lamps.json, tests/signal_lamps.cpp
  • Signal's motion lv/signal_motion.hpp gives Signal's durations (press 120 ms, enter 220 ms, settle 480 ms) and easings (out, in-out, and back, which overshoots), the same in every theme: lv::signal::motion.duration.enter, *lv::signal::motion.ease.out. They are a header of their own, so lv/signal.hpp costs what it did. lv/signal_motion.hpp, include/lv/signal/motion.json, tests/signal_motion.cpp
  • State and bindings lv::state holds a measure (an mp-units quantity with an integer number), an lv::counter, a one-member struct, a bool, an enum, a color or a pointer. lv::bind ties a property to it. A state keeps its own list of watchers, so following it costs no LVGL subject; raw() makes an lv_subject_t for C code on first use. state.hpp; state.cpp, state_plain.cpp
  • Lists lv::each(tracks, &track::id)[row] shows a row template for each row of an lv::list<T, N>, whose capacity is fixed at compile time. A change touches the widgets of its own row. lv::bind(&track::title) follows a field of a row, and .selected makes a state follow the selected row. See Lists. list.hpp; lists.cpp, lists_selection.cpp, lists_printer.cpp, examples/lists
  • Repetition by reflection lv::for_each<E>(part) makes one part for each enumerator of an enum (lv::but leaves some out), lv::for_each_field<T>(part) one for each member with an [[=lv::caption{"key"}]], and lv::for_each<items>(part) one for each record of a constant array. The compiler expands them into the children of the tree: no list, no allocation. lv::name_of and lv::like derive a text or a member from an enumerator's name. See Repetition. repeat.hpp, tree.hpp; for_each.cpp, fail/for_each_*.cpp, examples/repeat
  • Option lists .options = {"100%", "75%", "50%"} is joined by the compiler into LVGL's text and kept in read-only memory, so a dropdown copies nothing. Which setters take a list is found by name, and a test checks the names against LVGL's doc comments. lv::options_of<E, lv::but<...>> makes one option for each enumerator, with its name or the text of lv::option_text<E>, and .selected = lv::bind(state) of a state of that enum follows the choice both ways. See Option lists. options.hpp, detail/option_docs.hpp; options.cpp, options_docs.cpp, examples_widgets_roller.cpp, examples_widgets_dropdown.cpp
  • Concepts for parts A part is a function that returns a piece of tree, and constrains its parameters with the public concepts: lv::tree_handler, lv::event_handler, lv::dependency, lv::state_value, lv::tree_node, lv::view_value, lv::style_value, lv::font_value, lv::token_value and lv::token_of. A captureless lambda is a handler in a constexpr tree, and a state can be a template argument. A wrong argument is refused at the call, and a lambda with a capture says why. See Concepts for parts. view.hpp, computed.hpp, state.hpp, tree.hpp, style.hpp, values.hpp; concepts.cpp, handlers.cpp, fail/part_*.cpp, fail/handler_capturing_lambda.cpp, examples/parts
  • lv::computed and lv::effect A value derived from states, bound to a widget like a state, and code that runs when states change. The dependencies are fixed at compile time; nothing is registered at run time. computed.hpp; computed.cpp
  • Coroutine tasks lv::task<T> on LVGL's loop. view.next().clicked and every other event, lv::sleep, lv::first, lv::spawn. A deleted widget cancels the task. lv::spawn(task, owner) starts a task that ends with a widget. task.hpp; task.cpp
  • Animation lv::animate(widget, {.property = {from, to}}, time) for a property that takes one number: a whole number, a length, an angle or an opacity. The result says whether it ran to its end. animate.hpp; animate.cpp
  • A display that follows a state display.follow(mode, {lv::signal::day, lv::signal::dark}): the theme of the state's value is the display's theme, and setting the state restyles every widget in place, with no allocation once the screen was drawn. What a theme gives follows; a node's own token colors and looks do not. The active screen and the three layers are restyled; the themes have one shape. display.hpp, theme_styles.hpp; theme_follow, theme_restyle, examples/theme_follow
  • Animate style properties lv::animate(label, {.opa = {0 * pct, 100 * pct}, ...}, time) moves a local style value of the main part: every style property that takes one number (opacity, translate_x, transform_scale, arc_width, ...), with its own type. lv::in<"knob", "pressed">(view) names the part and the state. A name that is also a widget setter (width, x) stays the widget's in the plain call. animate.hpp; animate_style, fail/in_*.cpp, editor/api_uses.cpp
  • Easing curves for animations A fourth argument of lv::animate: a name from lv::ease (LVGL\'s six animation paths and its 24 named curves), a cubicBezier design token, or an lv::bezier as in CSS. Without it the value moves at one speed. easing.hpp, animate.hpp; animate.cpp
  • Other threads lv::ui_scheduler: post() from any thread, co_await ui.schedule() in a task. Hosted only. Needs no LVGL build option. ui_scheduler.hpp; ui_scheduler.cpp, under ThreadSanitizer
  • Match lv::match with lv::is<...> and lv::otherwise. For an enum, every enumerator needs exactly one arm. match.hpp; match.cpp
  • Runtime JSON and patches lv::runtime<...>::load builds a screen from a document. apply changes properties by id. A refused document leaves nothing behind. runtime.hpp, json.hpp; runtime_ui.cpp, json.cpp
  • Agent kit The widget tree as JSON, a PNG of a widget or a screen, and an MCP server with four tools inside the host program. See Agents. dump.hpp, png.hpp, mcp.hpp; agent_kit.cpp, examples/agent/
  • Settings One settings file for the whole program, lvgl26_settings(app lvgl26.json): allow forbids allocation, threads, files or floating point, and each part of lvgl26 that needs one is a compile error that names the key; rules relaxes the library's strictness; limits takes a value and a unit. A misspelled key, a wrong type and a wrong unit are compile errors; a library compiled with other settings stops the link. A build without the file specializes lv::cfg. The keys are data (docs/reference/settings.json, with a JSON Schema), and a skill proposes a file. config.hpp, detail/settings.hpp, cmake/settings.cmake; settings.cpp, settings_file.cpp, settings_zero_cost.cpp, fail/settings_*.cpp, fail/restrict_*.cpp
  • Compile cost, every night Valgrind counts the instructions that GCC runs for eight probe files, so the number is the same on every run. A change beyond a threshold opens an issue. See the trend. tools/compile_cost.py, tools/metrics/probes.json; compile_cost_tools
  • Example ports: LVGL get_started The four LVGL get_started examples, rewritten with lvgl26. Each gives the same pixels as the C original. examples/lvgl/get_started/; examples_get_started.cpp
  • Example ports: LVGL widgets 81 of the 163 widget examples of LVGL v9.6.0, in the label, button, arc, bar, slider, switch, checkbox, led, line, obj, buttonmatrix, dropdown, roller, spinbox, spinner, textarea, image, scale and keyboard groups. Each draws the same pixels as the C original on both LVGL versions. The others are listed with what each needs. examples/lvgl/widgets/; examples_widgets
  • Example port: Slint's printer panel The printer demo of Slint (MIT): a side bar, seven pages that slide in, a queue and bound controls. Each page is its own tree in its own source file, and compiles on its own. examples/ports/slint/printer/; ports_printer
  • Example port: Qt Design Studio treadmill The treadmill panel of Qt Design Studio (BSD-3-Clause): a splash screen and a main screen in three looks. examples/ports/qt/treadmill/; ports_treadmill
  • Migration pages From Qt Quick, From Slint and From TouchGFX: each concept of the toolkit next to lvgl26's answer, and what is not there yet. The readiness table is in the Migration section below. docs/from-*.md; docs_check
  • Runs on a microcontroller The slice (a compile-time tree, a label bound to a state, a task) is built for an Arm Cortex-M4 with -fno-exceptions -fno-rtti and run in QEMU every night. Measured: 269 KB of code with LVGL's default configuration, 1052 bytes of LVGL's heap for the screen, 128 for the task. examples/mcu, cmake/arm, tools/arm-run.sh

Planned

Not on main yet.

None of this is available today. The order may change.

  • Example ports: more of LVGL LVGL's remaining widgets, layouts, styles, event, anim and scroll examples, each compared pixel for pixel with the C original. Then larger demo screens. examples/README.md
  • Importers Offline host tools that convert existing UI descriptions to the lvgl26 JSON schema. For a migration they take the form of skills with helper scripts, one for each toolkit. Migration gap
  • Several windows, and a close request a task awaits One wait over all sources of the application's loop, so several windows each wait on their own events; today the first source that can wait owns the wait, and another window's events are read at the next step. A close request that a task can co_await, once the window is a type of lv::. A setting for how a hidden display stops drawing: switching off marking, as today, or hiding the screen object. docs/research/input-devices.md, docs/research/visibility.md
  • import lv; The library as a C++ module, next to the headers.
  • Linter, profiler, debugger Tools that a person or an agent can drive, exposed through the agent kit.
  • More documentation, for people and agents The reference, generated by reflection and as data; guides and explanations; walkthroughs of the ports and a decision guide for each toolkit; an error catalogue; skills for agents that write C++, design with Signal and port from another framework.
  • Components Components that hold state and a view, used several times in a tree. Migration gap: unblocks Qt Component, Slint @children, TouchGFX containers
  • Long lists A list that keeps the rows that fit and refills them as they scroll in, over a count and a function that gives a row. Views that sort or filter a list without copying a row. docs/research/lists.md
  • Design showcase One design system, Signal, for a family of eight devices: mood boards and the system are done (see Design); the device screens and their lvgl26 firmware follow. design/signal
  • The browser, through WebAssembly An lvgl26 application, written once, built for WebAssembly and running in the page: a nightly job builds a counter and the bouncing ball with a GCC from trunk plus a third-party WebAssembly back end, compares their frames with the host build, and runs them in headless Chrome. Limits: that compiler is not a release, -O2 only (-Os fails in GCC), a patched <coroutine> header, input from the page is one pointer, the test suite of lvgl26 does not run on this target, and the image takes about 27 minutes to build when its Dockerfile or pinned scripts change. examples/wasm/, docs/research/web-target.md
  • Android Automotive OS and Android A manufacturer's own screens as native code, built with a GCC 16 cross compiler for Android and drawn into the window of a native activity. Not tried yet. docs/research/targets-and-safety.md
  • iOS Apple's compiler has no reflection yet, so there is no build. docs/research/targets-and-safety.md
  • A route for products with a safety goal lvgl26 has no safety certificate, and its compiler is not qualified. Two routes are studied. One is the main UI beside a small certified renderer that draws the telltales. The other is a second back end over LVGL Safe, the library LVGL writes for certification. docs/research/targets-and-safety.md
  • Design tool adapters Adapters that write tokens.json from a design tool, so that tokens are never copied by hand. Figma, Penpot and Claude Design, driven by agents. Migration gap
Migration

Coming from another toolkit.

What lvgl26 covers of Qt Quick, Slint and TouchGFX, and what a port still has to work around. Written from docs/migration/coverage.json, updated 2026-11-25.

What blocks a migration

The first two are built first. The rest is ordered by what each unblocks, and the order may change.

  • Components Reusable parts with their own state, parameters and slots, used several times in a tree. Unblocks: Qt Component; Slint component and @children; TouchGFX custom container
  • Lists and repeaters from a model A list, a repeater or a scroll list built from a model that changes, with a fixed capacity on small devices. Unblocks: Qt Repeater and ListView; Slint for over a model; TouchGFX scroll lists; the printer queue
  • Translations and text resources Text per language, plural forms and a switch of language at run time. Unblocks: Qt qsTr; Slint @tr; TouchGFX text resources; LVGL label_translation
  • A style that follows a state A style property bound to a state, so a theme or a look can change in place instead of mounting the tree again. Unblocks: Slint's four printer themes; the three looks of the Qt treadmill; dark and light switching
  • More gradients Diagonal gradients and gradients with several stops. Today a gradient is vertical or horizontal with two colors. Unblocks: the printer panel's tiles and color button; designer-made backgrounds
  • LVGL's symbols with a drawn font A font drawn from a TrueType file holds no LVGL symbol, and no token names LVGL's own font. A drop-down list draws its arrow in the font of its indicator part, which inherits it (lv_dropdown.c), and LVGL's theme sets a font on the screen only (lv_theme_default.c). Limits

Known limits.

Read these before you plan a product on it.

Compiler and platform

  • GCC 16.2 or newer only, with -std=c++26 -freflection. Reflection is a hard dependency. Clang cannot compile the code yet, so clang-tidy cannot analyze it either.
  • CMake 3.30 or newer and Ninja.
  • No precompiled header with lvgl26's headers in it. With GCC 16.2 a precompiled header silently drops the precondition checks of templates, so a broken precondition goes unnoticed. This is GCC bug 128909; GCC's development branch has it too. CMake's target_precompile_headers on a target that includes lvgl26 is such a header.
  • Headers only. There is no import lv; yet.
  • One microcontroller is proven, in an emulator. The slice runs on a Cortex-M4 in QEMU. No real board, no display driver and no other processor family has been tried, and there is no size budget yet.
  • A run-time .set({...}) needs about 3.5 KB of stack on a Cortex-M4. One .set({.value = 60}) takes 3,504 bytes at -Os (LVGL v9.6.0; 3,528 with the v10 pin), and so does a set with a named style or a look. A style written inline as lv::style({...}) is built in the call and adds about 2.6 KB: 6,120 bytes. The budget is 4 KB for a set of plain properties, a named style or a look, checked every night with -fstack-usage (tools/stack_budget.py); on a small stack, name the style or use a look. A tree built by the compiler and a property bound to a state are not affected.
  • A program without allocation runs no task. A task's frame is taken while the program runs, so "allocation": false makes lv::spawn a compile error until tasks get a fixed region of memory. The Cortex-M4 slice runs a task, so it does not forbid allocation yet. A restriction covers lvgl26's own functions, not the program's own code, and allow.files does not cover LVGL's own file drivers yet.
  • ThreadSanitizer runs on Linux only.
  • The v10 line is a pinned commit. LVGL v10 has no release yet and keeps moving.
  • Early. Version 0.0.1. Names and signatures can still change.

Language and library

  • Designated initializers must be in the order of the props: the id, the properties, the styles, then the handlers, each group alphabetical (.id, .range, .value, .style, .on_clicked). This is a C++ rule for members in declaration order, and tools/order_properties.py moves the properties of existing code.
  • A misspelled or misordered member is reported as could not convert '{...}' to props<"arc">. GCC does not name the member in that case.
  • A quantity in a state needs an integer number for now.
  • mp-units is yours to add. lvgl26 has no unit system for application values and does not include one.
  • Animations take one number per property, and one property for each call.
  • Hosted parts: lv::ui_scheduler, the PNG writer and the MCP server allocate or use the C library's files. They are not for a freestanding build.
  • Runtime documents: text values are at most 127 characters and are not unescaped. At most 32 nodes can have an id. Handlers, bindings and pointers cannot come from a document.
  • The MCP server blocks while it waits for a line, and speaks over stdin and stdout only.
