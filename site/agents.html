AI-agent ready

An agent that can see the screen it builds.

lvgl26 puts a Model Context Protocol server inside the program that shows the UI. An agent loads a screen, changes it, reads the widget tree and takes a screenshot. It works on real LVGL widgets, and only within the limits the host sets.

01

The loop: load, patch, dump, screenshot.

Four tools close the loop between what an agent intends and what LVGL draws.

  1. Tool 1

    load_documentBuilds a screen from a JSON document, in place of the one loaded before. A refused document changes nothing.

  2. Tool 2

    apply_patchChanges properties of the loaded screen by id.

  3. Tool 3

    dump_treeThe widget tree as JSON: type, id, place in pixels, readable properties, children.

  4. Tool 4

    screenshotThe screen as a PNG. Returned as an image, or written to a new file if the host allows it.

The agent compares the tree and the picture with what it wanted, then sends the next patch.

Wrapped here to fit. On the wire each message is one line.

A recorded session, run as a test

What the host answers

The test examples_mcp_host feeds this session to the example host on every build and checks the answers in order:

  • id 3 answers with the text loaded.
  • id 4 answers with the text applied.
  • id 5 answers with the tree, where the arc now has the value 60.
  • id 6 answers wrote .../mcp_host_screen.png, and the file is there.

A refused call is not a protocol error. It is a tool result with "isError": true and a text such as unknown_widget: chart or bad_value: 5, which the agent can read and act on.

02

The server lives in your program.

There is no separate tool to install and no simulator to keep in step. The program that shows the UI answers the agent.

How it fits

You list the widgets. Reflection does the rest.

The widgets in <> are the ones a document may use. Their property tables are generated by reflection from the same structs as the compile-time tree, so a document and C++ code accept the same names.

  • handle() takes one message and returns the answer. serve() is handle() for every line of a stream.
  • To give the program to an agent, register it as an MCP server with the stdio transport.

03

Screens from JSON, at run time.

The MCP tools sit on lv::runtime, which you can also use directly: for UI sent by a tool, a server or a test.

The document format

A node is a type, an id, properties and children

Values are written the way a person would write them:

  • numbers, true or false, and strings for text
  • "120px", "50%" or "content" for lengths
  • "90deg", "300ms", "#rrggbb"
  • an enumerator by name, in full ("LV_ALIGN_CENTER") or by its last part ("center")
  • a list for a property that takes several values

A document that is refused leaves nothing on the screen. The error says which of nine kinds it is, and names the piece of the document it is about.

lv/dump.hpp

The tree, without looking at pixels

Per widget the dump gives its type, its id if a document gave it one, its place on the screen in pixels, and its properties. A property is listed when reflection finds the getter of its setter: lv_arc_get_value for lv_arc_set_value.

The text goes to a sink, piece by piece. Nothing is allocated and nothing is thrown.

04

What an agent can and cannot do.

An agent gets a small, typed surface. The host decides how large it is.

It can

  • Build a screen from the widgets the host listed, under the widget the server was given.
  • Change properties by id on the screen it loaded.
  • Read the widget tree with places, sizes and property values.
  • Get a PNG of the screen as an image in the answer.
  • Write a new PNG file into one directory, if the host named one.
  • Read why a call was refused: the kind of error and the piece of the document, cut to 200 characters.

It cannot

  • Use a widget the host did not list. The answer is unknown_widget.
  • Set a property that does not exist, or give a value of the wrong kind.
  • Attach code. Handlers, bindings and pointers cannot come from a document.
  • Leave a broken screen behind with a bad document: nothing of a refused document stays.
  • Call anything else. There are four tools. Another name gets Unknown tool.
  • Make the handler fail with a bad message. Anything that is not a request gets a JSON-RPC error on one line. A fuzz target feeds the handler whatever a client could send.
05

The security rules of the screenshot tool.

It is the only tool that can touch the file system, so it has the strictest rules.

RuleWhat it means
No files by defaultA server writes no files unless the host names a directory in .screenshot_directory. Without one, a call with a name answers this server does not write files. A call without a name still returns the picture.
A name, never a pathThe client gives the name of a file: letters, digits, ., _ and -, ending in .png, not starting with a dot, at most 128 characters. The host's directory is put in front of it.
New files onlyThe file is made new. A file of that name that exists is not replaced, and a symbolic link of that name is not followed. The answer is file_exists.
One directoryWith a directory, the client can make new *.png files there, and nothing else.
tests/agent_kit.cpp

Tested with 20 names that must be refused

Among them an absolute path, ../, a subdirectory, a hidden file, a space, a backslash, an escaped slash, a drive letter, ~, $HOME and *. The test checks that each is refused and that no file appears in the directory.

06

Protocol and limits.

Plain facts for the person who wires it up.

Protocol

  • JSON-RPC 2.0, one message per line, over stdin and stdout. Batches are refused.
  • Revision 2026-07-28: no handshake. Every request names the revision and the client's capabilities in params._meta. server/discover tells what the server can do.
  • Revisions 2025-11-25, 2025-06-18, 2025-03-26 and 2024-11-05: a client that starts with initialize. ping is answered.
  • A notification is never answered. A method the revision does not have gets Method not found.

Limits today

  • Hosted only. The server allocates and uses <cstdio>. It is for a development host, not for a microcontroller.
  • serve() blocks. Nothing else of the program runs while it waits for a line.
  • stdout belongs to the protocol. Keep LVGL's log off it.
  • Screenshots need LV_USE_SNAPSHOT in the LVGL build.
  • Documents: text values are at most 127 characters and are not unescaped. At most 32 nodes can have an id.
  • Keys are compared as written. A client that escapes them ("tools\/call") is not understood.
